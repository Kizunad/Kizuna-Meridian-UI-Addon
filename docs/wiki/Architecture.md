# 职责与交互方向

## 模块边界

| 模块 | 职责 | 权威状态 |
|---|---|---|
| Meridian Mod Framework | 身体规则、真元账本、受校验请求与结果 | 持有并计算 |
| Human 及其他生物 Addon | 部位、组织、器官、经脉与固有配方内容 | 由框架统一保存实例 |
| UI Addon client | 身体状态展示、操作草稿、请求反馈 | 仅显示权威快照 |
| UI Addon server | 对接宿主身份、请求路由与框架处理器 | 复用宿主已有核心 |
| 可选 3D 内景 Addon | 在三维空间编辑同类真元操作 | 共用相同权威规则 |

UI 面向通用身体数据，不强制依赖 Human。器官数量、经脉名称、身体连接与可执行配方由已安装内容和宿主数据提供。后续可借助 Inventory UI Framework 的公开 API 注册窗口；经脉业务协议仍由经脉框架定义。

## 界面方向

采用 XML + owo-ui，先完成身体概览与简易操作，再扩展编辑体验。第一片建议先显示部位、组织、器官、经脉和局部真元库存，沿已有连接选择供给目标；人体聚气可以作为接入场景。

最小操作流程为：

1. 读取宿主授权的身体快照与当前修订。
2. 玩家选择摄入器官、加工配方或已存在的运输连接。
3. UI 构造框架 Protobuf 请求，交给宿主执行。
4. 显示成功或拒绝原因，刷新权威状态并提供调整入口。

现有协议提供 `GetBodySnapshot`、`GetTissueCapability`、`IntakeQi`、`StartOrganRecipe`、`TransportQi` 等入口。器官配方完整目录的客户端同步、可发现的操作能力及真实网络桥接仍需后续接入设计，不能仅凭客户端硬编码视为已完成。

## 交互约束

客户端只能提交操作意图。身体身份、权限、环境来源、可信时间、实际可用真元、配方内容和执行结果仍由宿主与框架校验；客户端不上传快照覆盖身体。

UI 可保存选中项、窗口布局和编辑草稿。动画与进度插值只负责展示，不逐帧扣真元或推进寿命。单机接入也经过同一权威请求路径。

运输、器官加工、成长与突破属于框架通用算子和内容附属配置，界面只调用已具备的能力。三维内景作为另一个可选附属演进，不成为简易操作的前置。
